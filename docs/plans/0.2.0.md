# 0.2.0 落地计划

状态：2026-10-26 核心工程实现完成，M1–M5 完整里程碑验收通过（限本计划的文字预制作与本地单写入者范围）。逐项证据、范围和保留项见[最终验收](../validation/v0.2.0-final/README.md)。
日期：2026-10-25。

## 1. 版本目标与边界

让一个多集短剧项目能够持续创作、中断恢复、准确返工，并完成可核对的剧本交付。

本版本继续采用本地文件、Skill 和 Python 标准库 CLI，保持单写入者模型。创作和语义审查由 Skill/审稿者执行，工具承担可确定的结构、引用、版本、状态和文本一致性检查。

本版本不包含 Web UI、多人实时协作、模型调用调度、自动生成视频、自动发布、通用生产图编辑器和完整长篇小说改编系统。不以新增 Skill 数量作为成果指标。

0.1.0 基线：37 个 Skill、17 项自动测试、单集完整示例；已有版本依赖失效、锁定基线保护、问题状态协议和交付包。沿用这些机制，避免另建竞争状态来源。

## 2. 核心使用场景

1. 从一集试写开始，确认方向后追加后续集，保留既有产物与版本。
2. 完成某批创作后中断；再次进入时，明确当前进度、阻塞原因、所需输入和下一步工作。
3. 写后续集时，查询指定集结束时的人物知情、道具归属、关系变化及未回收伏笔，并回查正文证据。
4. 修改前集或上游设定，识别失效内容，按依赖顺序修订或复核；旧审核和旧交接不得冒充有效结果。
5. 收到指定交付包的下游反馈，关联问题、修订版本和回验记录，再生成可核对的新包。
6. 全季完成后审查人物弧线、冲突升级、信息释放和伏笔兑现，明确哪些维度通过、需修订或未验证。

## 3. 数据与实现原则

- `project.json` 继续作为产物版本、依赖和问题状态的唯一机器来源。新增批次、反馈、交付记录如进入该文件，需明确协议版本与迁移规则。
- 正文是实际剧情事实的依据；大纲记录计划。结构化连续性记录必须引用正文版本与稳定定位，不能自动把计划转成事实。
- 全局状态索引是可重建的派生物，不允许独立修改后成为另一套事实来源；输入失效时索引也应失效。
- 旧 Markdown 继续可读、可登记；新增机器能力缺少必要字段时报告“未验证/需补录”，不得伪造补全。
- 不要求解析任意 Markdown。先定义本仓库模板的最小可解析约定，保留自由叙事文本；非标准旧稿采用显式适配或人工核对。
- 自动规则通过不等于故事质量通过。审核覆盖、执行方式和证据版本需要单独记录。
- 保留整文件依赖失效作为安全基线。对象和集场级影响分析先辅助人工判断，不自动让下游恢复有效。
- 所有写入继续保留锁定稿、拒绝危险覆盖、使用原子写入；查询、预览和计划命令不修改项目。

## 4. 里程碑与需求

以下命令名是拟议接口，开发时可以调整；能力边界和验收结果不随命名改变。

### M1：可以安全续作的项目管理

**R01 集数扩展**

- 增加追加集数操作，生成缺少的模板并更新项目登记。
- 已有集 ID、文件、版本和集序保持不变；重复追加给出明确结果。
- 本版只支持末尾追加；插集、重排和删除延后，避免引入依赖重写。

**R02 问题生命周期**

- 提供 `issue add/list/resolve/reopen/accept`，替代日常手改 `issues`。
- 记录问题位置、影响产物、证据、被复核版本及状态变更历史。
- P0 不可接受例外；关闭问题必须绑定当前受影响版本；接受例外需记录实际责任人与依据，不推断授权。
- 上游登记涉及已关闭问题时，明确列出需要重开的项目。提供一次原子执行的显式选项，或先重开再登记；不静默沿用旧结论。

**R03 恢复与批次检查点**

- 增加 `next`：按目标范围列出缺失/失效/被问题阻塞的产物、原因、所需输入、对应技能和建议执行顺序。
- 增加批次检查点：覆盖集、输入快照、完成项、未决问题、下批入口、必须回读位置。
- 恢复时重新检查当前文件，不能把检查点当成当前有效性的证明。
- 提供供人阅读的结果及稳定 JSON 输出，便于总入口技能使用；不自动运行模型或批准阶段。

**M1 验收**：从 EP001 项目追加 EP002–EP003，原文件和快照不变；创建问题后能阻塞对应关口；中断恢复能给出正确的最早阻塞点；版本变化不能复用旧问题关闭依据。

### M2：多集连续性与整季审查

**R04 可追溯的连续性索引**

- 定义最小结构化记录：对象 ID、状态类型、改变前后、故事时间（可选）、叙事集序、正文版本、集场/对白或动作定位。
- 由连续性技能从已写正文提取；工具验证字段、引用和版本，汇总索引。
- 支持查询截至某集的对象状态、状态变化历史及原文位置。角色知情与观众知情分开记录；闪回不直接覆盖当前状态。
- 信息缺失、来源冲突或记录失效时明确返回未知/冲突/待复核，不自动选择一个答案。

**R05 伏笔计划与实际对照**

- 使用稳定伏笔 ID 关联计划投放/回收与实际证据。
- 列出未投放、已投放未回收、到期未回收、已回收和已取消项；取消需有原因。
- 区分尚未写到回收集与已完成范围内遗漏；合理延后以计划修订记录为依据。

**R06 全季审核与关键技能深化**

- 扩展现有审核入口，支持指定集范围或全季审查；单独保存范围明确的报告。
- 覆盖人物弧线、冲突升级、重复节拍、信息释放、伏笔兑现和结局铺垫。
- 强化单集节拍、对白、连续性和修订技能：补诊断方法、正反例、修订策略及复核清单。
- 机器检查事实字段和覆盖范围；动机、情感效果、重复感等语义判断必须附实际文本证据。

**M2 验收**：三集样例中可查询角色与道具历史；能定位预置的跨集知情冲突、道具状态冲突和遗漏伏笔；来源失效时索引不可继续被称为有效；整季报告明确已读范围及未验证维度。

### M3：准确返工与反馈闭环

**R07 变更影响计划**

- 基于版本依赖列出直接、间接受影响产物，以及建议复核顺序。
- 有对象引用证据时补充受影响集场；没有时保留文件级范围，不声称精准定位。
- 区分确定的版本失效、内容差异，以及需要语义判断的潜在影响。
- 为每项记录“需改写/复核后无需改写/待判断”及证据；依赖刷新仍需新修订号和复核说明。
- 为非锁定稿明确历史内容保留策略：优先新路径存稿；只有登记快照而没有旧正文时，不承诺能够生成完整文本差异。

**R08 反馈到问题到回验**

- 记录反馈来源、交付包 ID、集场/对白/资产定位、证据、归属和关联问题。
- 支持反馈的待分诊、处理中、待回验、已关闭状态，引用关联问题而不复制问题状态。
- 区分剧本问题与制作实现问题；无法映射到已知包时保留待核实。
- 关闭反馈需有实际回验证据；剧本修改完成不等于下游已经接收或验证。

**M3 验收**：修改 EP001 后，受影响后集、审核、索引与交接被识别；按顺序复核恢复；未受影响的独立范围不被无依据阻塞；反馈可追溯到旧包、问题、新稿和回验，旧包保留。

### M4：可核对的交付

**R09 正文与交接确定性核对**

- 明确正文中的稳定场次、对白、说话者和资产引用格式，建立受支持模板的提取器。
- 核对正文、交接数据和可选 JSON 中的对白文本、说话者、引用、场次覆盖和版本。
- 明确允许的格式归一化规则；不能把对白删改当成空白差异忽略。
- 报告区分一致、不一致、未验证；不支持的输入格式不得报告全部通过。
- 不要求用户必须采用 JSON 交付；机器核对可使用内部派生数据，可读交接包仍然是一等产物。

**R10 交付记录与接收状态**

- 为交付包分配稳定 ID，保存文件清单、来源快照、核对结果和可选的被替代包 ID。
- 明确预制作交付与制作锁定状态，避免结构通过被误读为制作批准。
- 支持登记待接收、已接收、退回及实际依据；生成包不自动变为已接收。
- 支持导入已提供的配音/样片实测时长，记录来源与对应正文版本，对照估算偏差；不在本版生成配音。

**M4 验收**：对白漏行、说话者错误、旧版本导出都不能被标为核对通过；生成新包后旧包不覆盖；反馈和接收记录准确绑定包 ID；缺少实测数据时保持未实测。

### M5：端到端验证与发布

**R11 可复现的多集案例与回归集**

- 优先扩展《归还》为完整三集案例，包含跨集知情、道具流转、伏笔回收、批次中断和交接。
- 建立独立错误样例，不污染正常示例：提前知情、道具冲突、漏收伏笔、旧审核、旧交接、缺失复核证据。
- 完成一次明确标为模拟的下游反馈演练：旧包 → 反馈 → 问题 → 修订 → 复核 → 新包 → 模拟回验。
- 自动测试验证确定性规则；Skill 评测记录实际输入、输出、发现问题及人工判断，不用管线单测代替创作质量评测。
- 关键语义错误用例重复执行并记录漏检/误报。发布前明确评测样本和可接受结果；单次通过不能宣称稳定。
- 更新 README、操作手册、协议、相关技能与模板；增加套件引用完整性检查及 0.1.0 项目迁移示例。

**M5 验收**：新用户可照文档跑通完整案例；原有测试通过，新需求对应测试通过；实际创作审核、模拟反馈和真实接收证据在文档中清楚区分。

## 5. 开发顺序与交付单元

按下列顺序推进，每个单元完成实现、针对性测试、文档和示例后再进入下一项：

| 单元 | 工作内容 | 前置依赖 |
| --- | --- | --- |
| 1 | 数据协议设计、兼容策略、基线与验收用例 | 无 |
| 2 | 问题操作与追加集数 | 1 |
| 3 | 下一步建议、批次检查点、总入口恢复流程 | 2 |
| 4 | 连续性记录、索引、伏笔对照 | 1、2 |
| 5 | 范围/全季审核、关键技能方法与错误样例 | 4 |
| 6 | 变更影响计划、反馈状态与复核流程 | 3、4 |
| 7 | 正文/交接核对、包身份与接收记录、实测回填 | 4、6 |
| 8 | 完整三集演练、迁移、使用文档和发布验证 | 全部 |

三集案例从单元 1 开始设计，随功能逐步补齐，不能到最后才首次试用。实现不要求按上表机械拆成固定数量的提交；保持每个提交可审查、可验证即可。

暂不承诺日历工期。先完成单元 1，确定协议变更和文本解析范围，再根据实际开发节奏估算；范围调整优先延后界面和便利功能，保留恢复、返工、交付与多集验收主链。

## 6. 发布门槛

- 0.1.0 示例和历史锁定基线保持可验证；新增字段缺失时有明确兼容行为。
- 如升级项目协议，提供只读预检和显式迁移；迁移前备份，失败不留下半迁移状态；重跑不破坏已有结果。
- 仓库版本号与项目/交接协议版本分别管理，不因发布 0.2.0 就机械同步协议编号。
- 三集正常案例完成全部目标流程；所有预置确定性错误均被对应规则发现，并有正常对照避免全量误报。
- 连续性与整季审核的语义用例有真实执行记录、人工评审结论和已知限制。
- 任何过期索引、旧审核、旧交接或未回验反馈都不能被描述为当前已通过。
- 交付核对明确覆盖范围；无法核对的内容必须标未验证。
- 不为通过验收编造独立审稿、实际配音、下游接收或批准记录。
- 发布前才更新 VERSION 和 CHANGELOG；规划阶段不修改当前发布版本。

## 7. 主要风险与控制

| 风险 | 处理 |
| --- | --- |
| 结构化数据增加作者负担 | 由技能提取、工具校验；正文保持可读；避免同一信息手工维护多份 |
| 索引遗漏导致错误确信 | 保存来源、覆盖范围与有效性；缺失显式返回未知 |
| 精细影响分析遗漏依赖 | 整文件失效继续兜底；本版不自动豁免复核 |
| 任意 Markdown 难以可靠解析 | 限定模板契约，非标准输入显式降级或适配 |
| 技能评测存在波动 | 使用固定问题样例、正常对照、重复执行和人工复核 |
| 新需求导致重写整个 CLI | 先按状态、索引、交接边界渐进拆分，避免提前框架化 |

## 8. 第一项可执行任务

开展“0.2.0 数据契约与验收设计”：定义追加集数、问题事件、批次检查点、连续性记录、反馈和交付身份的最小字段；确定它们的唯一存储位置、依赖关系、兼容行为与命令输入输出；为三集案例列出状态变化和错误注入位置。

产物应包含协议草案、需求到验收用例映射，以及至少一个由 0.1.0 项目恢复/迁移的示例。此任务完成后开始单元 2 的实现。
