# 0.3.0 Harness 资产改进落实计划

状态：M0–M5 已完成；后续经用户授权推送和发布，详情见[发布记录](../validation/v0.3.0/release.md)。实际证据见 [阶段验收](../validation/v0.3.0/README.md)，下文为实施与验收要求。
日期：2026-11-05。基线：0.2.1 / `9e67946`。上一轮分析中本地 78 项 unittest 通过；实施前重新确认基线。

## 1. 目标与边界

按“历史评测解耦 → 效果对照 → 任务上下文包 → 按失败模式优化技能与复核范围”的顺序推进。目标是回答并改善三个问题：技能是否提高任务质量、全新上下文能否可靠接续工作、局部返工需要多少无关复核。

暂定以 0.3.0 组织本轮工作，完成发布验收后才修改 VERSION 和 CHANGELOG。维持 Python 3.9+ 标准库、本地文件、单写入者模型；保留 37 个 Skill 的现有职责及旧项目读取能力。

本轮不增加技能数量，不引入多人并发写入、大规模性能优化、Web UI 或通用模型调用框架。安装工具、真实配音与外部制作交接留待后续；本轮不把模拟接收当作真实验证。制定计划不启动模型评测、子代理或外部服务。

## 2. 基线与主要改动位置

| 已观察到的情况 | 改动入口 | 本轮处理方式 |
| --- | --- | --- |
| 历史 freeze 的哈希直接校验工作目录规则文件 | `tests/test_semantic_protocol.py`、`scripts/prepare_semantic_round.py` | 历史快照与当前候选分别维护 |
| 语义校验器固定读取一套 cases | `scripts/validate_semantic_output.py` | 显式接收数据集，保留旧调用兼容性 |
| 现有语义成绩来自固定短文本，缺少无技能对照 | `docs/validation/v0.2.1/semantic/` | 保留原结论，另建新实验 |
| next 提供阶段、技能、输入 ID，恢复材料仍需人工拼接 | `pipeline.py` 的 next_steps、checkpoint、continuity_index | 增加只读任务上下文生成能力 |
| impact 有候选位置，但文件级依赖仍决定失效传播 | `pipeline.py` 的 prerequisites、impact | 先测量，再试点对象级复核建议 |
| 部分子技能主要由原则和边界组成 | 高频创作、审计子技能及共享 references | 仅针对有证据的失败补充方法和示例 |

本表中的相对路径均相对于仓库根目录。现有历史验证报告、原始输出、评分、oracle 和 freeze 保持原字节；任何补充说明放在新目录。

## 3. 里程碑与推进顺序

| 阶段 | 交付物 | 前置条件 | 完成条件 |
| --- | --- | --- | --- |
| M0 基线与契约 | 基线报告、实验协议草案、任务包契约草案 | 无 | 明确兼容边界、指标、样本与记录格式 |
| M1 历史评测解耦 | 历史规则快照、双入口准备器、回归测试 | M0 | 修改当前技能不破坏历史校验，篡改历史快照仍被发现 |
| M2 建立效果对照 | 冻结输入、A/B/C 原始运行、逐项评分、失败分类 | M1 | 所有计划运行都有结果或失败记录，可以决定保留/精简/修订 |
| M3 任务上下文包 | 只读命令、契约、恢复演练、成本对照 | M2 | 新上下文可按包接续任务，材料版本可核验，成本与效果可比较 |
| M4 有针对性的改进 | 技能候选、复核范围试点、保留集报告 | M3 | 仅合入有证据收益且无关键回归的候选；无收益也如实结项 |
| M5 集成验收 | 兼容演练、文档、验收报告、发布候选 | M1–M4 | 工程结果与语义结论分开报告，所有未验证项明确列出 |

每阶段按“契约/夹具 → 实现 → 验证 → 报告”形成可独立审查的改动。不以日历工期代替完成条件。M2 的数据集和阅读材料规模决定主要评测成本，先完成试运行再执行完整矩阵。

阶段门槛是继续工作的证据要求，不增加逐阶段用户审批。执行能力缺失时明确记录受阻部分，继续可独立完成的工程工作；不得用旧成绩或当前作者自审替代未执行实验。

## 4. M0：固定基线与验收协议

实施事项：

1. 记录提交、Python/系统环境、工作区状态；运行现有 unittest、规模测量和新旧示例演练。
2. 盘点历史校验对工作目录文件的引用，包含 v0.2.0-final 的示例绑定；区分“历史归档完整性”与“当前版本兼容性”，两者分别保留测试。
3. 在临时副本复现：修改当前规则使历史哈希检查失败；next 恢复任务需要补读哪些材料；一次局部变更引起多少派生产物待复核。
4. 制定 `docs/design/0.3.0-contract.md`：历史快照寻址、实验 run manifest、任务包字段、退出码、旧接口兼容和只读范围。
5. 在新验收目录记录结果，不覆盖过去的测试日志。

交付位置：`docs/validation/v0.3.0/baseline/`、`docs/design/0.3.0-contract.md`。

验收：三类观察均有可重复步骤；已知限制与实际缺陷分开；现有失败若出现，先诊断并登记，不自动归因于新改动。

## 5. M1：历史证据与当前技能解耦

实施事项：

- 在新归档目录保存历史评测实际使用的 cases、规则及评分所需材料，附来源提交、原路径、SHA-256 与旧 freeze 的映射。仅接受与旧哈希一致的字节；找不到时报告缺失，不重建或猜测历史内容。
- 旧 freeze、oracle、原始输出和评分不改写。新归档测试从历史快照读取；当前技能的结构、链接与行为另行验证。
- 准备器区分历史复现入口与当前候选入口。当前候选每次生成不可覆盖的 run 目录，绑定自己的规则快照、数据集版本与提交；不得借用旧 freeze 表示新规则已验证。
- 输出校验器显式接收 cases 路径或实验 manifest；原有单参数调用保留旧数据集行为。校验器仍只检查结构与引用，不生成语义结论。
- 当前运行包检查必要的传递依赖。现有 templates.md 是导航，当前任务若需模板正文，应实际打包对应模板；历史复现仍保持当时读取集合，并说明缺失边界。
- 归档完整性与当前示例兼容性分别测试，避免解耦时意外删除兼容保障。

验收用例：在临时工作区修改当前 Skill，历史归档测试仍通过；改动历史快照、案例或输出字节时被拒绝；当前运行准确记录新哈希；历史准备结果不含 oracle/其他轮输出；缺必要依赖时给出具体文件；旧校验器调用仍有效。

完成后允许进入 M2。此阶段不修改创作方法，避免同时改变评测工具和被评测对象。

## 6. M2：建立有对照的效果基线

### 6.1 对照设计

同一模型及可取得的版本、同一任务、同一项目副本、相同工具权限、执行预算和输出要求，比较三个条件：

| 条件 | 提供材料 | 要回答的问题 |
| --- | --- | --- |
| A 无技能 | 用户任务、项目材料、完成工具操作所需的统一 CLI 帮助 | 模型在没有写作技能规范时能完成多少 |
| B 精简技能 | A + 当前任务必需的职责、边界、最小检查表 | 简短规则能否获得主要收益 |
| C 完整技能 | A + 现有按需路由的技能及共享依赖 | 完整资产是否进一步提升质量，成本增加多少 |

“完整”沿用按需读取，不强塞全部 37 个技能。B 的内容在看实验结果前冻结；三个条件拥有相同用户事实与任务硬约束，避免把信息缺失误当技能效果。记录宿主已有指令/已安装技能；无法排除泄漏时说明局限，不宣称纯净的无技能实验。

### 6.2 样本与运行量

- 另建 24 个新任务：路由与范围控制、写作、连续性审查、局部修订、中断恢复、交接各 4 个。
- 每类预先划分 2 个开发任务、2 个保留任务，共 12 + 12。配对变体、同源剧情必须同组，避免通过近似样本泄漏。
- 至少 4 个任务使用 12 集以上完整分场文本，开发集和保留集各至少 2 个；记录实际字数、文件数和可取得的 token 数。不能通过把六段摘要改称十二集满足长文本要求。
- 旧 12 个案例只作已知回归，不计入未见样本成绩。新样本包含正常对照、隐含信息、无关材料、前文缺失、上游变更和明确的局部任务边界。
- 先用开发集 3 个任务做工具与输出协议试运行，费用/耗时可测后再冻结正式实验。若根据试运行修改任务或规则，试运行结果单独保留，不混入正式得分。
- 正式开发集：12 任务 × 3 条件 × 2 次独立运行，共 72 次。各任务的条件执行顺序交错；每次使用新上下文，不继承其他输出。
- 保留集在 M4 候选冻结后执行：12 任务 × 现有基线/最终候选 × 2 次，共 48 次。以上不包含试运行和 M3 恢复专项；未跑满时明确报告覆盖范围。

评测材料准备、执行、评分三种职责分离。执行者不读取答案；评分隐藏条件名称，先做确定性校验，再做语义裁定。能力允许时由独立评阅者复核重大问题和争议；若只有作者 AI 评分，明确降低结论强度。记录可取得的模型身份，未知信息保留未知。本计划不指定子代理执行方式。

### 6.3 指标与决策规则

每个任务在运行前冻结必达项、禁止行为、允许的不确定性、问题等级与评分依据。创作任务采用约束检查和盲评比较，不规定唯一正确剧情。

| 指标 | 计算与用途 |
| --- | --- |
| 任务成功率 | 满足全部必达项且无关键违规的运行数 / 实际运行数；按任务类别分别列出 |
| 检出与误报 | 预置重大问题检出数 / 预置数；正常案例重大误报数 / 正常案例数；额外发现另行裁定 |
| 越界修改 | 改动允许范围外文件/章节且无必要一致性依据的运行数 / 有写操作的运行数 |
| 证据质量 | 引用定位正确与语义支持结论分别统计，不合并为一个通过标记 |
| 工作成本 | 可取得的输入/输出 token、耗时、工具调用、读入字节、补读次数、返工轮数 |

各轮原始输出、失败、超时和重试均保留；基础设施失败与模型任务失败分列。取不到 token 时用读入字节等代理指标并注明，不能写成 0 或冒称实际 token。报告分子分母和逐任务配对差异，不把两次运行当成两批独立题材样本。

决策：C 明显改善具体任务时保留对应规则；B 达到相同必达项且成本更低时优先精简；三者都失败时先检查任务材料与方法缺口。样本无法区分时结论为“尚无充分收益证据”，不强行宣布胜出。

交付：实验协议、输入/规则快照、run manifest、原始输出、评分证据、按失败模式排序的改进清单。M2 完成标准是得到可信比较结果，而非必须证明 C 更好。

## 7. M3：可验证的任务上下文包

拟增加只读命令，最终参数由 M0 契约固定：

```bash
python3 skills/ai-short-drama-writing/scripts/pipeline.py context PROJECT --scope EP003 --stage G3 --output /tmp/EP003-context
```

语义：scope/stage 选择目标，目标与项目状态不匹配时列出阻塞项，不静默改为执行其他阶段。默认输出到新目录，拒绝覆盖；不登记产物、不修改 project.json、不提升审核状态。保留现有 next 输出字段和行为。

任务包包含：

- 任务目标、当前阶段、结束条件；来自用户的写入范围单独传入或附加，不能由下一步建议推定新的授权。
- 必读技能/规则、产物路径、版本和哈希；区分完整来源与便于阅读的摘录。
- 相关人物/道具状态、伏笔、未决问题、检查点变化，以及对应原文证据位置。
- 允许写入的产物种类、建议验证/登记命令及尚缺参数；建议命令不自动执行。
- 来源快照、生成时间、截取规则、缺失和过期项、证据定位状态与语义复核状态。

复用 next/index/impact 的事实，不维护第二套状态机。摘要不替代正文，取不到可靠定位时明确要求补读原文。包使用前重新核对来源哈希；来源改变即提示重建，不能凭旧包继续宣称版本有效。新上下文的实际改稿仍写入指定项目，包内来源副本只用于阅读。

工程验收：正常、缺文件、旧散文、过期依赖、错 scope、未决问题、生成后源文件变化、输出已存在；项目文件和清单在生成前后字节一致。不能将用户任务或项目正文中的文本当成宿主指令执行。

效果验收：从开发材料派生至少 6 个恢复场景，覆盖正常接续、上游变更、缺前文、局部修订、未决问题和旧格式；比较原恢复流程与任务包，各运行 2 次，共至少 24 次。要求没有新增越界修改、伪造通过或使用已知过期输入；分别报告任务成功率、补读量和成本。若包更长或效果下降，缩减内容或保留为可选功能，不默认推广。

## 8. M4：按证据修改技能与缩小复核范围

### 8.1 技能改进

按 M2/M3 失败记录选择最多 3 个高频技能或共享规则位置。每个候选必须附“失败案例 → 原因假设 → 修改 → 预期改善 → 回归检查”的记录。

优先补充有区分力的正反例、判断步骤和失败恢复方法；例如对白目的与口吻、角色说法与客观事实、修订引起的必要关联变化。示例按需读取，避免增加所有任务的固定上下文。无证据支持的条款不加入。

先在开发集做每次只改变一个主要因素的比较；冻结最终候选后执行 M2 保留集矩阵。保留集出现问题时报告失败，下一轮使用新保留集；不反复针对同一保留集调参后继续称其未见。

合入标准：目标失败类型改善，未引入关键证据/范围/版本回归；报告改善与退化的具体任务。若质量相同而成本下降，可作为精简收益；若收益无法确认，保留现有技能并归档尝试。不得以总平均分掩盖关键违规。

### 8.2 依赖粒度试点

首先测量至少 6 个局部变更：角色外观、人物知情、世界规则、对白措辞、伏笔计划、前集末状态。分别建立实际需复核范围的有据判定，与现有文件级传播结果比较。

只有当无关复核构成可见成本时，增加对象/规则/场次引用索引，用于排序候选阅读位置和解释影响路径。索引记录来源版本与覆盖程度，缺失或不确定时回退到文件级范围。

本轮不允许对象级建议自动清除 STALE、跳过 gate、刷新依赖或批准产物。验收要求固定夹具中的关键受影响位置无遗漏，并报告建议复核量减少了多少；实际漏检或维护成本高于收益时撤回试点。

是否改变权威依赖和状态协议留待后续独立设计，不作为本轮必须交付项。

## 9. M5：集成、兼容与发布验收

- 现有 unittest、规模测量、新旧示例演练持续通过；新增测试覆盖实际契约与风险，不以测试数量作为进度指标。
- CI 继续运行无需模型的确定性检查、归档完整性与运行包结构检查。模型评测单独执行并保存证据，CI 不把旧评分当成新版本语义测试通过。
- 旧 project.json、旧 CLI 调用及旧例预期的 UNVERIFIED 行为保持兼容。需要新可选字段时明确读取/写入规则，不自动迁移旧项目。
- 文档同步到 README、操作手册和实际受影响的 Skill；清楚标示 context 的只读性质及能力限制。
- 在 `docs/validation/v0.3.0/README.md` 列出工程验收、语义对照、恢复实验、候选去留、未完成项和实际运行环境。
- 本地通过与远端 CI 通过分别记录；未执行的模型、环境、真实制作验证不可标为通过。
- 完成上述范围后再决定正式版本与更新发布文件。本计划不包含自动推送、打标签或发布。

## 10. 执行记录与首个实施批次

建议验收目录按 baseline、archive、experiments、context、candidates 分组。每次运行绑定输入、规则、输出及评分哈希；每个阶段报告已完成、失败、未验证与下一步，不修改历史结果来消除失败。

首个实施批次只做 M0 + M1：

1. 重跑基线并固化当前技能变更与历史校验耦合的复现。
2. 从可验证来源构建历史快照与映射，保留所有原始历史字节。
3. 调整准备器、校验器及归档/兼容测试，验证双入口。
4. 保存验收结果，再冻结 M2 的对照协议和样本。

首批不修改创作规则、不实施对象级依赖，也不把实验准备完成记为效果提升。
